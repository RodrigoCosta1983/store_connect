6. AUTORIZAÇÃO — MATRIZ NÃO HERDADA

Comum às cinco operações propostas:
- request.auth.uid obrigatório; sem autenticação: unauthenticated.
- Ler users/{uid}; perfil ausente, papel inválido ou revoked: permission-denied.
- storeId canônico vem exclusivamente desse perfil; validar string não vazia/ID válido e ler stores/{storeId}. Nunca aceitar loja como autoridade no payload.

7. CONTRATO COMUM DE PAYLOAD E ERROS

Objeto simples, chaves explícitas; rejeitar campos extras e payload ausente/null/array. UID, role, storeId, nomes legados, timestamps, audit e estado de arquivamento não são recebidos como autoridade.
IDs existentes: strings opacas, case-sensitive, não vazias, sem espaços externos, '/' ou IDs reservados/inválidos de documento; respeitar limite Firestore de ID. Não exigir auto-ID de 20 caracteres e não converter números/nomes em ID.
categoryIds obrigatório nas operações de vínculo/criação, array de 0..10 strings; validar antes de qualquer deduplicação. Duplicados, null, escalar e tipos mistos rejeitados. Não truncar nem limpar silenciosamente.
[] é intenção explícita de desvincular. Omissão nunca significa limpar.
Cada ID desejado deve existir em stores/{lojaDoPerfil}/categories/{id}, com nome canônico utilizável. Ausente ou só existente em outra loja: failed-precondition, categoria indisponível na própria loja, sem procurar nem revelar dados externos. Mesmo ID em duas lojas resolve somente o documento local.
Erros propostos: invalid-argument para formato; permission-denied para autorização; not-found para alvo na própria loja ausente; failed-precondition para categoria em uso/indisponível ou estado não suportado; aborted com motivo estável taxonomy-conflict para base obsoleta; already-exists para requestId reutilizado com conteúdo diferente; unavailable para falhas transitórias. Não incluir documentos privados na mensagem.

8. PAYLOADS PROPOSTOS

8.1 setProductCategories({productId, categoryIds, expectedTaxonomy})
Todos obrigatórios; nenhum opcional no primeiro incremento.
expectedTaxonomy é precondição, nunca fonte de persistência. Objeto com somente as chaves taxonômicas observadas no snapshot anterior: categoryIds, categoryId, categoryName. Chave ausente deve continuar ausente; null/''/[] não são equivalentes. Comparar presença e valor exatos na transação, inclusive ordem do array. Não usar preço/estoque como base do conflito.
Estados usuais antigos/new são representáveis em JSON. Tipos anômalos não representáveis, array inválido/acima de 10 ou projeções estruturais corrompidas retornam failed-precondition; não reparar por essa API normal. Órfão string pode ser retirado/substituído explicitamente pelo usuário no novo array válido, com audit antes/depois.
Transação: perfil, loja, produto, categorias desejadas, antes de qualquer write; validar base; atualizar somente os três campos e audit. Não criar produto ausente. Resultado: {success:true, productId, changed, categoryIds, categoryId, categoryName}. Esse retorno privado não altera DTO público.
Se estado já é exatamente o resultado desejado válido (inclusive projeção), retornar changed:false sem log; se base divergiu e resultado atual é outro, aborted. Reenviar não faz merge automático com a edição de outra aba.

8.2 deleteCategory({categoryId, expectedName})
Obrigatórios; expectedName é string exatamente observada, não nome usado para localizar categoria. Proposta de precondição contra renomeação entre diálogo e ação. Ausência atual após autorização pode retornar {success:true, categoryId, alreadyAbsent:true}, sem log e sem afirmar quem a excluiu.
Se existe e nome difere da base: aborted; se usada: failed-precondition/category-in-use. Sucesso real: {success:true, categoryId, alreadyAbsent:false}. Não apaga imagem Storage nem produto.

8.3 createCategory({requestId, name, imageUrl?})
requestId obrigatório, UUID aleatório estável por intenção, reutilizado em retries; validar formato/limite (36 caracteres da representação UUID). Não é categoryId nem autorização.
name obrigatório string, trim, não vazio. Proposta técnica de limite 100 pontos de código após trim: NOVA, depende de D4; não tratar como limite já existente. Preservar grafia/acentos/espaços internos.
imageUrl opcional, default ''. Se fornecido, string URL HTTPS de imagem no prefixo category_images da loja no bucket configurado, ou ''; proposta de limite 2048 caracteres. Validar no servidor, não aceitar URLs externas arbitrárias; não buscar URL na rede. Regra de imagens integra D4. Upload continua fora da transação Firestore.
ID da categoria novo gerado no servidor, estável durante retries da transação. Criar name/imageUrl/createdAt servidor; sem storeId redundante, isActive, campos de ordem/campanha ou categoria principal.
Audit de criação na mesma transação; receipt de idempotência conforme seção 12. Resposta {success:true, categoryId, replayed}. Não reutilizar categoria por nome sem escolha explícita.

8.4 renameCategory({categoryId, name, expectedName})
Obrigatórios. name passa pela mesma validação do CREATE; expectedName representa exatamente o nome anterior observado. Preservar ID, imageUrl e createdAt; update somente name e audit.
Se nome atual já é o novo nome normalizado: changed:false. Se diverge de expectedName e não é o desejado: aborted. Não precisa alterar todos os produtos nem batch de fan-out.
Resposta {success:true, categoryId, name, changed}.
Imagem não será escrita por esta operação; a edição direta de imagem só pode permanecer separada se futura proteção de name/política de metadados permitir. Não redesenhar Storage aqui.

8.5 createProduct({requestId, product, categoryIds})
Obrigatórios. Não aceita productId existente para sobrescrever. requestId com mesma semântica de criação de categoria. Produto novo recebe ID servidor; IDs existentes nunca mudam.
product: allowlist baseada no cadastro atual: name, price, quantidade, lotes, minimumStock, imageUrl; opcionais barcode, costPrice e fiscal. Não aceitar name_lowercase, createdAt, storeId, três campos taxonômicos, isArchived/archived* ou campos arbitrários dentro desse objeto.
Servidor deriva name_lowercase, timestamps e legado. Inteiros de estoque/mínimo/lotes devem ser seguros e não negativos, preço/custo números finitos não negativos; quantidade consistente com soma dos lotes quando usados. Datas em formato explícito convertido pelo servidor, sem confiar em Timestamp serializado arbitrário.
Fiscal só permitido conforme plano real lido no servidor; nunca confiar em isBusiness enviado pelo Flutter. Preservar os campos fiscais já usados, sem reformar regra tributária.
Limites exatos de nome de produto, quantidade de lotes, formato de datas, barcode/imagem e allowlist/tipos fiscais ainda precisam do subcontrato D9: não considerar essa callable pronta para implementação completa com um Map irrestrito.
Criação, validação das categorias e dual-write em uma transação, audit/receipt juntos. Resultado {success:true, productId, replayed}. Importação reutiliza a mesma capacidade com lote vazio e 0/1 categoria inicialmente.

9. CATEGORY IDS E LEGADO

Preservar o contrato B, explicitamente retomado por BR:
- categoryIds é canônico e ordenado para serialização; vínculo é semanticamente conjunto.
- Primeiro ID na ordem de inclusão define categoryId temporário; categoryName é nome atual dessa entidade lido na transação.
- Isso NÃO cria categoria principal de negócio. Não adicionar campo primaryCategoryId.
- [] grava categoryId=null e categoryName=null, não deleta chaves. Escolha já proposta em B para representar vazio consistentemente; os escritores atuais usam null ou ''.
- Os três campos são escritos atomicamente pelo servidor. Cliente não escolhe nome legado, não envia esses valores como resultado desejado.
- Array presente prevalece sobre singular na leitura, inclusive []; ausência permite fallback legado. Array inválido não autoriza fallback.
- Leitura/estoque/arquivamento/rename nunca materializam ou reparam array automaticamente.
- Rename altera somente categoria. categoryName persistido pode ficar antigo até uma gravação taxonômica explícita; futuros leitores devem resolver categories.name. Não propagar rename para milhares de produtos.
- DTO público atual ainda copia categoryName persistido. Resolver nomes atuais e DTO aditivo serão incrementos separados, antes de oferecer experiência multicategoria completa.

11. EXCLUSÃO SEGURA

Algoritmo proposto no Admin SDK, após autorização:
1. Na mesma transação, ler perfil/loja e categoria no caminho autorizado.
2. Conferir existência e expectedName.
3. transaction.get(products.where('categoryIds','array-contains',categoryId).limit(1)).
4. transaction.get(products.where('categoryId','==',categoryId).limit(1)).
5. Não filtrar isArchived. Qualquer resultado bloqueia, inclusive legado residual quando array está vazio/divergente.
6. Se ambas vazias e precondições de integridade atendidas, transaction.delete(categoryRef) + audit na mesma transação. Todas as leituras antes das escritas.
7. Falha de consulta/índice/timeout rejeita; nunca interpretar erro como ausência de uso.

Concorrência: TODO escritor autorizado de vínculos, inclusive criação/importação, deve ler as categorias desejadas dentro da mesma transação que grava o produto. A categoria lida também é o documento removido pela exclusão. Associação que serializa antes faz a consulta de uso encontrar o produto; exclusão que serializa antes faz a associação encontrar categoria ausente e falhar. Retries revalidam o estado.
Não basta consultar fora da transação e depois deletar, nem validar categoria fora da transação e depois batch de associações.
Não é necessário presumir que query vazia trava todo o intervalo; o desenho combina isolamento serializável com dependência explícita no documento da categoria em todos os escritores. Deve ser comprovado com testes concorrentes reais no Emulator antes da liberação.
O Admin SDK Node suporta transaction.get(Query). Não confundir com capacidades do SDK Flutter.
Não adicionar contador, coleção de relações ou documento lock: não há necessidade demonstrada para o contrato 0..10. Não introduzir contador que ainda poderia ser contornado pelos writers antigos.

categoryName legado:
Não é ID, pode estar obsoleto ou duplicado; não usar igualdade de nome como prova de vínculo nem reconstruir associação. Os escritores atuais produzem pares ID/nome, e os vínculos comprovados estão nos dois campos de ID.
Nome sem ID utilizável ou schema inválido é anomalia que esta auditoria de código não quantificou em dados reais. Duas queries por ID não provam ausência de todos os formatos corrompidos imagináveis. Para liberar exclusão em lojas legadas, D8 exige inventário somente leitura autorizado e tratamento explícito das exceções; não certificar esses dados sem inspecioná-los.
Se houver referência somente por nome, opção conservadora é manter exclusão bloqueada até resolução explícita, não inferir a qual homônimo pertence. Não propor varredura completa e normalização de todos os produtos em cada delete nem migração automática.

Referências adicionais: CatalogItems guardam productId, não categoria; solicitações guardam snapshots sem categoria; vendas referenciam produtos. AuditLogs/backups com nomes/IDs são históricos e não bloqueiam delete. Nenhuma coleção comercial/seção dinâmica operacional encontrada. Futuros referenciais exigirão extensão explícita da verificação.

12. CONCORRÊNCIA E IDEMPOTÊNCIA

Proposta D5: base taxonômica explícita, sem revision nova inicialmente. Comparar na transação resolve duas abas sem forçar conflito de negócio por alterações de preço/estoque. Conflito devolve erro e exige recarga; não resolver silenciosamente por última escrita.
Transação pode fazer retry por qualquer alteração física do produto (inclusive estoque), mas após retry a comparação somente taxonômica ainda permite a intenção se os vínculos não mudaram. Não regravar campos operacionais lidos anteriormente.
Limite da comparação por estado: não detecta ciclo A->B->A (ABA). É suficiente apenas se o contrato for detectar divergência atual, não toda edição intermediária. Se auditoria de toda revisão for requisito, será necessário revision protegido contra cliente; RULES-A atual não protege um novo campo revision. D5 deve escolher explicitamente, sem adicionar campo desprotegido.

Retries de set/rename: se alvo já está no estado desejado, no-op sem log; se outra edição mudou o estado, conflito e não reverter. Não prometer resposta original ou exatamente uma execução a nível de transporte. Delete de alvo já ausente retorna alreadyAbsent, sem log duplicado; sem recriação de ID pelo backend.
Criação precisa idempotência durável: auto-ID novo por chamada duplicaria produto/categoria. Proposta de usar auditLogs existente como comprovante da criação, com ID determinístico derivado no servidor de loja+UID+operação+requestId (hash), e campos adicionais requestHash/resultId. A transação lê esse comprovante antes de criar; mesmo payload retorna o ID original, payload diferente rejeita. Não recria entidade excluída em replay; retorna replay histórico e o cliente recarrega existência atual.
Isso reutiliza coleção já protegida para escrita backend, sem inventar serviço de idempotência. É extensão proposta do contrato de audit (D5), não padrão já implementado. A retenção desse comprovante deve cobrir o período de retry e impedir reutilização de IDs; não pode ser limpo automaticamente enquanto garantir deduplicação. Sem aprovação, não considerar criação idempotente resolvida.
Gerar refs de entidade/log fora do callback de retry; nenhum upload, envio externo ou efeito irreversível dentro da transação. Autorizar novamente até no replay.

Cenários:
- Duas abas: primeiro commit altera base; segunda conflita salvo mesmo resultado idempotente.
- Importação versus edição: importação cria, não edita existentes. Deduplicação por requestId não garante unicidade por nome/barcode; análise de duplicados é distinta. Replays não sobrescrevem produto já criado/editado.
- Rename versus vínculo: transação de vínculo lê categoria; commit usa nome consistente nesse instante. Rename posterior não faz fan-out, por contrato.
- Delete versus vínculo: protocolo da seção 11; obrigatório também para importação.
- Duas exclusões: uma efetiva com log; outra já ausente.
- Callback/requisição repetido: regras de no-op, comprovante e conflito acima.
- Cliente antigo offline: ao sincronizar depois do corte, alteração taxonômica/criação antiga ou delete direto falha pelas Rules. Não aceitar version gate de UI como barreira; não reabrir permissão para permitir fila antiga. Atualização compatível/aviso são requisitos do rollout.
