2. DIAGNÓSTICO DE traceCategoryReads
Arquivo: functions/tests/products/createProduct.emulator.test.js:1701–1718.
O array reads é criado fora do callback de runTransaction. Toda repetição do
callback escreve no mesmo array, inclusive tentativas cujo commit aborta.
Além disso, transaction.get é substituído dentro de cada tentativa, sem
restauração por tentativa. O SDK reutiliza o mesmo objeto Transaction no loop:
uma tentativa posterior pode capturar o wrapper anterior e empilhar wrappers.
Assim, as contagens misturam tentativas e podem multiplicar registros de uma
mesma chamada. Não medem exclusivamente as leituras da transação concluída.

Evidência no SDK local (functions/node_modules/@google-cloud/firestore/build/
src/transaction.js): runTransaction, linhas 390–425, repete runTransactionOnce
no mesmo this; runTransactionOnce, linhas 434–449, chama updateFunction(this),
aguarda commit e faz rollback em erro. isRetryableTransactionError, linha 582,
inclui status 10 ABORTED, entre outros, sujeito ao limite de tentativas.
O log anterior c/c/c/r/r/r é compatível com esse defeito. Não permite afirmar
quantas tentativas ocorreram nem quantas leituras houve em cada uma. Por exemplo,
duas tentativas com wrappers acumulados podem registrar cada path três vezes.
Não houve telemetria por tentativa na E3-B para reconstruir a sequência exata.

Proposta de correção da instrumentação, NÃO APLICADA:
- separar registros por invocação do callback;
- instalar/restaurar transaction.get com finally em cada invocação, evitando
  wrappers empilhados;
- após runTransaction resolver com commit bem-sucedido, verificar os registros
  da última tentativa; manter as tentativas anteriores separadas para diagnóstico;
- não usar Set/deduplicação para ocultar leituras repetidas dentro da tentativa;
- preservar as expectativas de paths e testar a instrumentação com retry controlado.
Alterar a semântica dessa instrumentação exige decisão posterior conforme R1.
Nenhuma correção foi necessária/aplicada para executar os testes existentes.
